## 3. 발견된 버그

### 🔴 [Critical] 등록한 날짜가 화면에 하루 앞당겨져 표시됨

**재현 경로**: 프로모션 등록 화면에서 시작일 `2026-09-01`, 종료일 `2026-09-30`을 입력 후 등록 → 목록/상세 화면에 `26.08.31~26.09.29`로 표시됨 (스크린샷 `07-list-with-new-promotion.png`, `08-detail-partner-EC01.png` 비교).

**근거 (네트워크 응답 원문)**:
```json
{"start_date":"2026-08-31T15:00:00.000Z","end_date":"2026-09-29T15:00:00.000Z", ...}
```
입력한 `2026-09-01`이 `2026-08-31T15:00:00.000Z`로 저장/응답됨 — 이는 KST(UTC+9) 기준 `2026-09-01T00:00:00+09:00`과 정확히 같은 시점이다.

**근본 원인**: `docs/8-schema.sql`의 `start_date`/`end_date` 컬럼은 `date` 타입(16~17행)이다. `pg` 드라이버가 `DATE` 컬럼을 서버 프로세스의 로컬 타임존(KST) 기준 자정으로 파싱해 JS `Date` 객체를 만들고, Express의 `res.json()`이 이를 `.toISOString()`으로 직렬화하면서 UTC로 환산돼 9시간(하루 경계에서는 날짜 자체)이 밀린다. 프론트엔드(`formatDate` — 목록/상세/캘린더 공통)는 이 UTC ISO 문자열을 그대로 `.slice(2,10)`으로 잘라 쓰기 때문에, UTC 오전 9시 이전 시각이 되는 모든 날짜가 하루 앞당겨져 보인다.

**영향 범위**: 목록 화면, 상세 화면, 캘린더(날짜 셀 배치 자체가 어긋날 수 있음 — 겹침 판정에도 영향 가능) 등 날짜를 표시/비교하는 모든 화면.

**권장 조치**: 백엔드에서 `date` 컬럼을 문자열로 반환하도록 `pg` 파서 설정을 조정하거나(`pg.types.setTypeParser`), 프론트엔드에서 서버 타임존을 고려한 변환을 거치는 대신 백엔드가 애초에 `YYYY-MM-DD` 문자열을 그대로 내려주는 쪽이 가장 단순하고 근본적인 해결책이다. 이번 리포트 작성 세션에서는 이 문제를 관찰만 하고 수정하지 않았다 — 수정 여부는 별도 확인 후 진행 요망.

**✅ 후속 조치 (2026-08-21, 이 리포트 작성 다음 세션에서 처리 완료)**: `backend/src/db/pool.js`에서 `pg.types.setTypeParser(1082, ...)`로 `DATE` 컬럼(OID 1082)을 JS `Date` 객체 대신 원본 `'YYYY-MM-DD'` 문자열로 반환하도록 오버라이드해 위 권장 조치대로 수정했다. 서버 재시작 후 `GET /promotions/:id`, `GET /promotions?from=&to=` 응답 모두 타임존 변환 없이 정확한 날짜를 반환함을 재확인했다(백엔드 테스트 64/64 유지). 이 리포트의 본문은 발견 당시 기록을 그대로 보존하고, 이 문단만 후속 조치 결과로 추가한다.

## 4. 개선 포인트 (버그는 아니지만 실사용 시나리오에서 관찰된 사항)

1. **캘린더 셀 데이터 과밀**: 반복된 테스트/시드 데이터가 누적된 상태에서 특정 날짜 셀(9월 1일 등)에 프로모션 항목이 10개 이상 나열되어 셀이 매우 길어짐(`24-calendar-september-cluttered.png`). 실사용 환경에서 특정 기간에 프로모션이 몰리면 동일 현상이 발생할 수 있음 — 셀 내 항목 수 제한("+N개 더보기") 같은 보완이 필요할 수 있음. 어제(2026-08-20) UX 검토에서 지적한 "목록 페이지네이션 부재"와 같은 근본 원인(전체 데이터를 그대로 렌더링)의 캘린더판 사례.
2. **404/찾을 수 없음 화면에 복귀 경로 없음**: 위 E6 참고. 오류 문구만 뜨고 헤더도 없어 "목록으로" 같은 링크가 없다.
3. **캘린더가 취소됨/반려됨 상태의 프로모션도 그대로 표시함**: 시나리오 6 테스트 중 이미 `취소됨` 처리된 "국물떡볶이" 프로모션이 9월 1일 캘린더 셀에 계속 노출됨(`24-calendar-september-cluttered.png`에서 확인). `9-plan.md` FE-7 완료조건 문구("진행 중·예정 프로모션")를 엄격히 적용하면 종결 상태(반려됨/취소됨)는 제외되어야 하나, 현재 구현은 날짜 겹침만으로 필터링해 상태를 구분하지 않음.

**✅ 후속 조치 (2026-08-21)**: #1, #3을 함께 해결했다. `CalendarPage.jsx`에서 `cancelled`/`rejected` 상태 프로모션을 캘린더 표시 대상에서 제외하고, 날짜 셀당 최대 3건만 표시한 뒤 나머지는 "+N건 더" 텍스트로 요약하도록 변경했다(`MAX_VISIBLE_PER_DAY`). #2(404 복귀 경로)는 이전 라운드(critical #3)에서 이미 해결됨.

## 5. 기타 관찰 사항 (버그 아님)

- 로그인/회원가입 최초 진입 시 브라우저 콘솔에 `POST /auth/refresh 401` 에러가 2회 로깅됨 — 이는 세션 복구 부트스트랩 로직이 유효한 refresh 쿠키가 없는 상태에서 의도적으로 시도하는 정상 동작이며, 화면에는 아무 영향 없음(로그인 폼이 정상적으로 뜸). 다만 브라우저 개발자도구를 보는 사용자에게는 "에러"로 보일 수 있어 참고로 남김.
- 테스트 중 생성한 계정/프로모션은 정리하지 않았다(요청 범위 밖) — DB에는 이번 세션 포함 여러 차례의 E2E 테스트 데이터가 누적돼 있다.
