# E2E 테스트 리포트 (프로덕션 배포본) — CJ프레시웨이 프로모션 협업 앱

- **실행 일시**: 2026-08-21
- **대상**: 프론트엔드 `https://cjk-007-fe.vercel.app` + 백엔드 `https://cjk-007-be.vercel.app` (Supabase Postgres 운영 DB)
- **실행 방법**: Playwright MCP로 실제 Chromium 브라우저를 구동해 배포된 프론트엔드를 UI 그대로 조작. 보조적으로 curl로 백엔드 예외 케이스(401/400/409) 직접 확인.
- **기준 문서**: `docs/4-user-scenario.md`(시나리오 1~6), `docs/1-domain-definition.md`(EC-01~EC-06)
- **성격**: 이 문서는 로컬 dev 서버 대상 리포트(`e2e/E2E-REPORT.md`)와 별개로, **실제 배포된 프로덕션 환경**을 대상으로 한 결과다. 이전 라운드(같은 날 진행된 두 차례의 프로덕션 점검)에서 발견·수정된 항목(날짜 타임존 버그, 크로스오리진 세션 쿠키 버그, 404 처리, 취소 버튼 라벨 혼용)이 실제로 안정적으로 유지되는지 재확인하고, 그때 다루지 않았던 흐름(수정 후 승인, 반영거부, 미저장 변경 확인창, 컬럼 정렬, 반응형, 재오픈)까지 보완해서 검증했다.

## 사전 조치: 테스트 데이터 정리

이전 라운드에서 curl 쉘 스크립트로 만든 테스트 데이터 일부가 인코딩 손상(`U+FFFD` 치환문자)된 채로 운영 DB에 남아있었다(예: `ProdE2E□□□»...`). 원인은 앱이 아니라 쉘 스크립트의 인코딩 처리였음을 DB 원본 바이트(`encode(..., 'hex')`)로 확인했고, 관련 사용자 6명·프로모션 4건·변경요청 2건을 삭제해 정리했다. 사용자가 직접 만든 계정(`CJ관리담당자`, `가상_협력사`)은 손대지 않았다.

## 1. 시나리오별 실행 결과

### 시나리오 1 — 협력사 담당자의 프로모션 제안 등록
- 회원가입(역할/소속사명/이메일/비밀번호) → `/login` 이동 — `prod-01-signup.png`, `prod-02-signup-success-redirect-login.png`
- 로그인 실패(EC-06) → 폼 상단 오류 메시지 — `prod-03-login-error-EC06.png`
- 로그인 성공 → 목록 화면(빈 상태) — `prod-04-list-partner.png`
- 등록 폼 필수값 미입력 제출 → 오류 표시, API 미호출 — `prod-05-register-validation-error.png`
- **[보완] 작성 중 취소 시 확인창** → "작성 중인 내용이 사라집니다. 계속하시겠습니까?" 뜨고 취소 선택 시 폼 유지 — `prod-06-unsaved-changes-guard.png`
- 정상 등록 → 목록에 '제안됨'으로 반영, 한글 정상 표시
- **[보완] 목록 컬럼 클릭 정렬** → "제목/품목" 헤더 클릭 시 `▲` 인디케이터 표시 — `prod-07-list-sort-indicator.png`

### 시나리오 2 — CJ프레시웨이 담당자의 프로모션 승인
- 상세 화면 EC-01 안내(협력사에게 액션 버튼 없음) — `prod-08-detail-partner-EC01.png`
- CJ프레시웨이 계정으로 승인/수정후승인/반려 버튼 노출 확인
- **[보완] "수정 후 승인" 흐름**: 편집모드 진입 → 필드 pre-fill 확인(`prod-09-edit-mode.png`) → **미저장 변경 확인창**(편집 중인 내용이 사라집니다) 취소 선택 시 편집모드 유지 확인 → 조건 텍스트 실제 변경 후 저장 → `승인됨` + 변경된 조건 반영 — `prod-10-edit-then-approve-success.png`

### 시나리오 3 — CJ프레시웨이 담당자의 프로모션 반려
- (이전 라운드에서 검증 완료, 이번 라운드는 승인 경로 위주로 보완 진행 — 반려 자체는 이전 리포트에서 한글 정상 저장까지 확인됨)

### 시나리오 4 — 변경요청 등록 및 반영
- 승인 이후 상태에서 변경요청 등록 → "승인후변경" 태그 표시, 협력사에게 반영완료/반영거부 버튼 없음 — `prod-11-changerequest-post-approval.png`
- **[보완] 반영거부 처리**(이전 라운드는 반영완료만 검증) → `반영여부: 반영거부`로 정상 갱신 — `prod-12-changerequest-rejected.png`

### 시나리오 5 — CJ프레시웨이 담당자의 프로모션 취소
- 사유 입력 후 취소 → `취소됨` 상태 즉시 갱신
- **[신규 발견]** 취소됨 상태의 상세 화면에 재오픈(FR-8, P1) 버튼이 없음 — `prod-13-cancelled-no-reopen-ui.png` (아래 3장 참고)

### 시나리오 6 — 캘린더에서 프로모션 현황 조회
- 주 탭 전환 시 `GET /promotions?from=...&to=...` 재조회 발생(네트워크 로그로 확인)
- CJ프레시웨이 계정의 `/promotions/new` 직접 접근 시 목록으로 리다이렉트(역할 가드)

## 2. 이전 수정사항 재검증

| 항목 | 재검증 결과 |
|---|---|
| 날짜 타임존 버그(`pg` DATE 파서) | 유지됨 — 입력한 날짜가 그대로 표시(`27.03.01~27.03.15` 등) |
| SameSite=None 크로스오리진 쿠키 | 유지됨 — 새로고침/딥링크 진입해도 세션 유지 |
| 404 처리(헤더+복귀버튼) | 유지됨 — `prod-15-404-not-found.png` |
| 캐치올 라우트(완전히 없는 URL) | 유지됨 — "존재하지 않는 페이지입니다" + 목록 링크 |
| "프로모션 취소"/"편집 취소" 라벨 분리 | 유지됨 — 이번 라운드 전체 흐름에서 혼동 없이 정상 동작 |

## 5. 신규 발견 사항 (버그는 아니지만 기록 필요)

### 재오픈(FR-8, P1) 기능이 프론트엔드 UI에 없음

- **현상**: 백엔드에는 `PATCH /promotions/:id/reopen`이 구현돼 있고(이전 라운드에서 curl로 정상 동작 확인됨), `종료`/`취소됨` 상태의 프로모션을 `검토중`으로 되돌릴 수 있다. 그런데 프론트엔드 상세 화면(`PromotionDetailPage.jsx`)에는 어떤 상태에서도 "재오픈" 버튼이 렌더링되지 않는다 — CJ프레시웨이 계정으로 `취소됨`/`종료` 상태 프로모션을 봐도 액션 영역이 완전히 비어있다(`prod-13-cancelled-no-reopen-ui.png`).
- **근거 문서와의 관계**: `docs/9-plan.md`의 FE-5 완료조건 4개(EC-01 안내, 상태별 버튼, 반려/취소 사유, 수정후승인)에는 재오픈이 포함되지 않았고, FE-8(반응형)까지도 재오픈 UI는 어느 태스크의 완료조건에도 명시되지 않았다. 즉 계획 문서 기준으로는 "완료조건 미달"은 아니지만, `docs/2-prd.md` FR-8이 살아있는 기능 요구사항이고 백엔드가 이미 구현된 이상, 프론트에서 호출할 방법이 없다는 것은 사용자 관점에서 "종료/취소된 프로모션은 영원히 되돌릴 수 없다"와 동일한 결과를 낳는다.
- **영향**: P1(우선순위 낮음, 시간 여유 있을 때 적용) 기능이라 MVP 출시를 막을 사안은 아니나, 실사용 시 CJ프레시웨이 담당자가 잘못 취소/종료 처리한 프로모션을 되돌릴 방법이 관리자 API 직접 호출 외에는 없다.
- **제안**: `PromotionDetailPage.jsx`의 액션 영역에 `['closed', 'cancelled'].includes(promotion.status)`일 때 "재오픈" 버튼을 추가하고 `useReopenPromotion` mutation 하나만 `usePromotionMutations.js`에 추가하면 된다(반려/취소와 동일한 패턴, 새로운 컴포넌트 불필요). 착수 여부는 사용자 판단 필요.
