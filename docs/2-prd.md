# PRD - CJ프레시웨이 프로모션 협업 앱 (v1.0)

> 기준 문서: `1-domain-definition.md` (v1.4). 본 PRD는 도메인 정의서의 MVP 범위를 벗어나지 않으며, 3일/1인 개발 제약을 전제로 작성한다.

## 1. 개요 및 배경

- **목표**: 협력사(식자재 제조·공급사)와 CJ프레시웨이 간 프로모션 제안·검토·승인·협의 과정을 하나의 서비스로 통합하고, 이력을 남겨 추적 가능하게 만든다.
- **문제 정의**: 프로모션 제안이 이메일·전화·엑셀로 산재되어 전체 현황 파악이 어렵고, 협의 내용이 기록되지 않아 맥락 추적이 어려우며, 승인 권한이 명확히 구분되지 않는다.
- **목표 사용자**:
  - 협력사 프로모션 담당자 (약 1,000명 이상)
  - CJ프레시웨이 상품/영업 담당자 (약 800명)
- **대체재/경쟁 환경**: 별도 경쟁 서비스보다 이메일·전화·엑셀 등 기존 수작업 방식이 실질적 대체재이며, 본 서비스는 B2B 프로모션 협업이라는 좁은 문제에 특화한다.

## 2. 목표 및 성공지표

- 프로모션 제안·검토·승인·변경 과정을 하나의 시스템에서 처리해 이메일/전화/엑셀 의존도를 낮춘다.
- 모든 상태 변경과 협의 내용(변경요청)이 프로모션 단위로 이력화되어 추적 가능하다.
- 협력사와 CJ프레시웨이의 권한(제안 vs 최종 결정)이 시스템상 명확히 구분된다.
- 별도의 정량 KPI(전환율, 매출 등)는 MVP 단계에서 억지로 설정하지 않는다. 단, MVP 오픈 후 "프로모션당 변경요청으로 처리된 협의 건수"를 정성적으로 관찰해 기존 이메일 대비 대체 효과를 확인한다.

## 3. 범위 (Scope)

도메인 정의서 9장의 MVP 범위를 그대로 인용한다.

### 포함
- 프로모션 제안 → 협의 → 검토 → 승인/반려 → 변경 → 일정/진행 현황 관리 (Promotion Collaboration & Governance)

### 제외
- 주문·발주·배송·재고 연동
- 주문/정산, 비용 정산 및 매출/ROI 분석
- 재고 실시간 연동
- 협력사 등급 차등(고객관리)
- AI 추천 및 외부 시스템 연계
- 포인트 적립
- 검색 기능
- 그 외 부가적이고 과한 기능

## 4. 기능 요구사항

각 항목은 도메인 정의서의 유스케이스(UC)/예외케이스(EC)를 근거로 하며, 우선순위는 P0(3일 내 필수) / P1(여유 있으면 포함)으로 표기한다.

| ID | 기능 | 근거 | 우선순위 |
|---|---|---|---|
| FR-1 | 회원가입/로그인 (협력사/CJ프레시웨이 역할 구분, 로그인 실패 시 오류 안내) | UC1, EC-06 | P0 |
| FR-2 | 프로모션 제안 등록 (기간/대상 품목/조건 입력, 필수값 검증 시 '제안됨' 상태로 등록) | UC2, EC-01 | P0 |
| FR-3 | 프로모션 검토/승인/수정/반려 (반려 시 반려사유 필수, 수정 후 승인 시 변경 내용 반영) | UC3 | P0 |
| FR-4 | 프로모션 취소 (CJ프레시웨이만 수행, 취소사유 필수) | UC3, EC-04 | P0 |
| FR-5 | 변경요청 등록 및 반영 처리 (협력사가 변경요청을 등록 → CJ프레시웨이가 반영완료/반영거부 처리, 승인후변경 여부 구분) | UC4, EC-01, EC-03 | P0 |
| FR-7 | 캘린더 조회 (월/주/일 단위로 진행 중·예정 프로모션 목록 표시) | UC6, EC-05 | P0 |
| FR-8 | 종료/취소된 프로모션 재오픈 (CJ프레시웨이만 수행, '종료'/'취소됨' → '검토중', 재오픈 이력 기록) | EC-02 | P1 |
| FR-9 | 프로모션 기간 중복 경고 (동일 대상품목 + 동일 공급사 기준, 1일 이상 겹치면 등록/승인 시 경고, 차단하지 않음) | EC-05 | P1 |

> P1 항목(FR-8, FR-9)은 3일 일정상 여유가 있을 때만 반영하며, 시간이 부족하면 다음 스프린트로 넘긴다.

## 5. 비기능 요구사항

- **UI**: 반응형 웹 UI 필수. 데스크톱 우선으로 설계하되 모바일 브라우저에서도 레이아웃이 깨지지 않도록 한다. 별도 모바일 앱은 고려하지 않는다.
- **성능**: 특별한 목표치 없이, 목록/캘린더 조회 시 일반적인 웹 서비스 수준의 응답 속도면 충분하다. 별도의 캐싱/최적화 인프라는 도입하지 않는다.
- **보안**: 로그인 인증 필수(모든 사용자는 인증 후에만 서비스 이용). 비밀번호는 해시 저장. 역할(협력사/CJ프레시웨이) 기반으로 API 접근을 구분한다. 그 외 세부 보안 정책(계정 잠금 등)은 MVP 범위 밖.
- **접근성(A11y)**: 이번 프로젝트 범위 아님.
- **가용성/인프라**: 별도 이중화, 오토스케일링 등은 고려하지 않는다. 1인 개발·최소 예산 전제로 단일 서버 구성.

## 6. 기술 스택 및 아키텍처 개요

- **프론트엔드**: React 19, 전역 상태관리 Zustand, 서버 상태/통신 TanStack Query
- **백엔드**: Node.js + Express
- **DB 접근**: pg (PostgreSQL 드라이버)
- **데이터베이스**: PostgreSQL 17

### 시스템 구성 (텍스트)
```
[React 19 SPA (반응형 웹)]
    - Zustand: 로그인 세션 등 클라이언트 전역 상태
    - TanStack Query: 프로모션/변경요청 등 서버 데이터 fetch/mutate
        |
        | HTTP (REST API)
        v
[Express 서버]
    - 인증(세션/토큰) 및 역할 기반 접근 제어
    - 프로모션/대상품목/변경요청 CRUD 및 상태 전이 로직
        |
        | pg
        v
[PostgreSQL 17]
    - users, promotions, items, promotion_items, change_requests
```

## 7. 일정 및 리소스 계획 (3일, 1인 개발)

| Day | 작업 범위 |
|---|---|
| Day 1 | DB 스키마 설계(users/promotions/items/change_requests), Express 기본 API 골격, 인증(FR-1: 회원가입/로그인), 프로모션 등록(FR-2) 기본 CRUD, React 프로젝트 셋업(Zustand/TanStack Query 연동) |
| Day 2 | 검토/승인/수정/반려/취소(FR-3, FR-4), 변경요청 등록/반영(FR-5) — 프로모션 상세 화면(변경요청+상태 변경)을 중심으로 구현 |
| Day 3 | 캘린더 조회(FR-7), 반응형 레이아웃 정리, 시간이 남으면 P1(FR-8 재오픈, FR-9 기간 중복 경고) 반영, 통합 테스트 및 마무리 |

- 1인 개발 기준이므로 기획/디자인/개발/테스트를 모두 동일 인원이 순차 수행한다.
- 별도 QA/디자인 리소스 없이 진행하며, 예산은 추가 인프라·외부 서비스(SaaS 등) 없이 최소화한다.

## 8. 리스크 및 오픈 이슈

- **일정 리스크**: 3일·1인 개발이라는 매우 타이트한 일정으로 인해 FR-8, FR-9(P1)는 미구현될 수 있다. 발생 시 다음 스프린트로 이월한다.
- **오픈 이슈 (도메인 정의서 인용)**: EC-03 재승인 — 승인 이후 핵심 조건 변경 시 재승인(Re-approval) 절차를 의무화할지 여부. 기본값은 미적용이며 결정 기한/담당자는 TBD. MVP는 기본값(재승인 없음)으로 구현한다.
- **범위 확장 리스크**: 주문/정산/AI추천/검색 등 요구가 추가로 들어올 수 있으나, 도메인 정의서의 MVP 제외 항목을 그대로 유지해 범위를 지킨다.
